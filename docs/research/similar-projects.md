# 유사 프로젝트 조사 (해커톤/공모전 운영 플랫폼 생태계)

조사일: 2026-09-08. 모든 항목은 GitHub 레포 자체(README/LICENSE/스타/최근 커밋) 또는 공식 사이트를 WebFetch로 직접 확인한 뒤 기록했다. 리스트업(listicle)만 보고 넣은 항목은 없으며, 확인이 부족한 부분은 6장에 명시했다.

## 1. 요약

HACKMAN은 "호스팅형 대형 플랫폼"(Devpost, HackerEarth, Devfolio, Taikai, DoraHacks 등)과 "특정 대학/동아리용 소형 OSS 툴"(Gavel, dribdat, JunctionApp) 사이의 중간 지점에 있는 자체 호스팅형 소규모~중형 공모전 운영 도구다. 규모나 기능 폭에서 대형 호스팅 플랫폼과 경쟁하는 게 아니라, 그런 플랫폼들이 보통 얕게만 지원하거나 아예 안 하는 세 가지— (1) 서버가 강제하는 대회 상태 머신, (2) LLM 태그 추출 + 규칙 기반 팀 추천, (3) WebSocket 없이 ETag 폴링으로 구현한 실시간 스코어보드 —를 조합한 게 특징이다. 판정 방식은 Gavel류의 페어와이즈(pairwise) 비교가 아니라 절대점수(absolute scoring) 평균 방식을 택했는데, 이는 대부분의 상용 플랫폼(HackerEarth, ScoreJudge 등)과 같은 노선이고 Gavel과는 명확히 다른 노선이다. 오픈소스 진영에서 HACKMAN과 같은 조합(운영 상태 관리 + 심사 + 팀 매칭 + 시상)을 통째로 제공하는 프로젝트는 찾지 못했다 — dribdat과 JunctionApp이 범위상 가장 가깝지만 팀 매칭에 LLM을 쓰지 않고, Gavel은 심사에는 강하지만 팀 매칭·대회 상태 관리가 아예 없다.

## 3. 가장 가까운 프로젝트 심층 비교

### Gavel (anishathalye/gavel)

Flask+PostgreSQL로 만든 프로젝트 엑스포 심사 시스템으로, HackMIT이 2015년부터 자체 심사에 써온 코드를 오픈소스로 공개한 것이다(스타 486, 포크 266, AGPL-3.0). 핵심은 절대점수가 아니라 **페어와이즈 비교 기반의 Crowd-BT 알고리즘**이다. 심사위원에게 "프로젝트 A와 B 중 어느 쪽이 더 나은가"만 반복해서 묻고, Bradley-Terry 모델(둘 중 하나가 이길 확률을 잠재 실력 점수의 차이로 모델링)을 심사위원별 신뢰도(annotator reliability)까지 함께 추정하도록 확장한 것이 Crowd-BT다. 시스템은 매 비교마다 "다음에 어떤 두 프로젝트를 비교시키면 랭킹에 대한 정보 이득이 최대인가"를 계산해 다음 매치업을 능동적으로 골라준다(액티브 러닝과 유사). 이 방식의 장점은 심사위원마다 절대 점수 기준(어떤 사람은 후하고 어떤 사람은 박함)이 달라도 상대 비교이기 때문에 캘리브레이션 문제가 원천적으로 없다는 것 — HACKMAN이 안고 있는 "심사위원별 절대점수 편차" 문제를 Gavel은 설계로 회피한다. 단점은 팀 수·심사위원 수가 커지면 필요한 비교 횟수가 늘어나고(각 프로젝트가 최소 N번은 비교돼야 신뢰 가능한 순위가 나옴), 결과가 "순위"이지 "몇 점"이 아니라서 시상 등급 컷을 명확한 점수로 설명하기 어렵다는 것, 그리고 대회 도중 실시간으로 몇 등인지 참가자에게 보여주기 어렵다는 것(비교가 끝나기 전까지 랭킹이 불안정)이다. Gavel에는 팀 매칭, 대회 상태 관리, 발표 타이머, GitHub 연동이 전혀 없다 — 순수하게 심사 한 기능만 하는 도구다.

### CTFd (CTFd/CTFd)

CTF(Capture The Flag) 대회 운영 프레임워크로 Flask 기반, Apache-2.0, 스타 6.8k로 이 조사에서 확인한 프로젝트 중 가장 활발하다(이슈 315건, PR 111건 오픈 — 유지보수 활발). 채점은 사람 심사가 아니라 "플래그 제출 시 정답 여부 자동 판정"이라 HACKMAN의 심사 도메인과는 다르지만, **실시간 스코어보드 아키텍처**가 참고할 만하다. CTFd는 WebSocket을 쓰지 않고 `/api/v1/scoreboard` REST 엔드포인트를 클라이언트가 폴링하는 구조이며, 공식 블로그(v3.3.0 릴리즈 노트)에서 팀 모드 스코어보드 쿼리를 20~30배 최적화해 62초 걸리던 응답을 2초로 줄였다고 밝히고 있다. 즉 CTFd도 "실시간성이 필요한 스코어보드를 폴링으로 푼다"는 점에서 HACKMAN과 같은 선택을 했고, 다만 최적화 지점이 다르다 — CTFd는 엔드포인트 쿼리 자체의 속도를, HACKMAN은 캐시(3초)+ETag 304 응답으로 네트워크/서버 부하를 줄이는 쪽에 집중했다. 두 접근은 상호보완적이며 동시에 적용 가능하다.

### dribdat (dribdat/dribdat)

"데이터 기반 해커톤과 육각형 팀을 위한 플랫폼"이라는 슬로건의 Python/Flask 올인원 오픈소스 툴(MIT, 스타 89, 커밋 3,220개로 오래 유지된 프로젝트). 시빅테크 스프린트, 크라우드소싱 이벤트 용도로 설계되어 챌린지 관리, 실시간 진행 로그, Git/Forgejo/Etherpad에서 데이터 수집, Slack/Discord/Mattermost 연동까지 지원한다. 심사는 절대점수나 페어와이즈가 아니라 큐레이션/투표에 가까운 방식으로 보이며(정확한 랭킹 산식은 README에서 상세히 확인하지 못함), HACKMAN처럼 서버가 강제하는 명시적 대회 상태 머신(모집중→진행중→심사중→종료)은 없어 보인다. 대신 다양한 외부 도구 연동에 강점이 있다 — HACKMAN이 아직 안 하는 "참가자 진행 상황을 Git 커밋 로그에서 자동 수집" 같은 아이디어는 참고할 만하다. 팀 매칭에 LLM을 쓰지 않고, 발표 타이머나 GitHub 파일 뷰어 프록시 같은 기능도 없다.

### JunctionApp (hackjunction/JunctionApp)

핀란드 Junction이 자기네 대형 해커톤을 실제로 운영하는 데 쓰는 올인원 플랫폼(AGPL-3.0, 스타 76, 커밋 2,490개). 등록→수락→제출→심사까지 한 파이프라인으로 묶는다는 점이 HACKMAN의 "Contest→Team→Submission→Judge→Score" 흐름과 구조적으로 가장 비슷하다. 특히 README에서 **Gavel의 페어와이즈 투표 방식을 자체 심사에 채택**했다고 명시하고 있어, "실제로 큰 해커톤을 운영해본 팀이 절대점수보다 페어와이즈를 선택했다"는 사실 자체가 HACKMAN의 설계 선택(절대점수)에 대한 유의미한 반증 사례로 볼 수 있다. 팀 매칭 기능은 README에서 확인하지 못했고, LLM 사용도 없다.

### ScoreJudge (scorejudge.com)

오픈소스는 아니지만(호스팅 SaaS, freemium), HACKMAN과 판정 철학이 가장 가까운 상용 제품이다. "각 채점 기준(criterion)마다 배점을 두고 합산하는" 절대 루브릭 점수 방식을 쓰며, 심사위원이 제출할 때마다 실시간으로 갱신되는 리더보드, 그리고 **최고점/최저점 자동 제외(outlier drop)** 기능을 제공한다. 이 outlier drop은 HACKMAN에는 없는 기능으로, 절대점수 방식이 안고 있는 "유독 후하거나 박한 심사위원 한 명이 평균을 왜곡한다"는 문제를 완화하는 실용적인 수단이다.

## 4. HACKMAN의 차별점

**진짜 특이한 것:**
- LLM 태그 추출(자유서술 bio → 기술스택/관심사/역할/숙련도) + 규칙 기반 추천 점수(빈 역할 45점, 관심사 겹침 25점, 빈 슬롯 20점, 스택 비중복 10점)를 **결합**한 팀 추천 — 조사한 팀 매칭 도구 중 이 조합을 하는 곳은 없었다. Devpost/DevMatch는 사람이 직접 훑어보는 필터링이거나(Devpost) GitHub 활동 데이터 기반 자동 분류(DevMatch, LLM 아님)였다.
- 심사중 대회 상태에서만 최종 라운드가 비공개이고, 시상식에서 등수 순서대로 리빌하는 흐름 — 확인한 프로젝트 중 이 정도로 세분화된 "공개 시점 제어"를 하는 곳은 못 봤다.
- 발표 순서/타이머에서 "교체 시간에는 타이머가 안 돈다"는 설계(늦는 팀이 다음 팀 시간을 깎아먹지 않게 함) — 자잘하지만 확인한 어떤 프로젝트 문서에도 이 디테일은 없었다.
- REST 폴링 + 서버 캐시(3초) + ETag 304 조건부 요청 + 탭 백그라운드 시 폴링 중단까지 갖춘 스코어보드 — CTFd도 폴링을 쓰지만 ETag 304 활용은 확인하지 못했다.
- 서버가 강제하는 대회 상태 머신(UI가 아니라 API 레벨에서 상태별 액션을 막음) — Gavel·dribdat·JunctionApp 어디에서도 이 정도로 명시적인 상태 게이팅은 확인 못했다.

**차별점이 아닌 것(대부분이 이미 함):**
- "스코어보드가 있다" 자체는 차별점이 아니다 — Devpost, HackerEarth, CTFd, ScoreJudge 전부 실시간 스코어보드를 제공한다.
- "심사위원별 점수 평균+판정 인원 표시" 자체도 흔하다 — ScoreJudge, HackerEarth 모두 동일.
- "동점자 공동 순위(1,1,3 스킵)" 같은 랭킹 규칙은 스포츠/대회 채점의 표준 방식이라 독창적이라 보기 어렵다.
- GitHub 저장소 뷰어(README/파일트리 iframe)는 DoraHacks의 "소스코드 리뷰" 기능과 개념적으로 겹친다 — HACKMAN은 여기에 캐시+프록시로 API 레이트리밋을 회피한다는 구현 디테일이 있지만, "심사위원이 코드를 직접 본다"는 아이디어 자체는 새롭지 않다.
- staff/participant/judge/guest 역할 분리는 사실상 모든 경쟁 제품의 기본 구조다.

## 5. 참고할 만한 설계 아이디어

- **Gavel의 Crowd-BT(페어와이즈)** — HACKMAN의 절대점수 평균 방식은 심사위원 간 채점 기준 편차(어떤 심사위원은 전체적으로 후하게/박하게 줌)를 구조적으로 보정하지 못한다. 당장 페어와이즈로 전환하는 건 과할 수 있지만, 절충안으로 ScoreJudge의 **outlier drop**(최고/최저 점수 자동 제외) 정도는 적은 비용으로 도입할 만하다. 혹은 심사위원별 평균/표준편차를 정규화(z-score)한 뒤 합산하는 방식도 고려할 수 있다.
- **JunctionApp이 실제로 Gavel의 페어와이즈를 택했다는 사실** — 대형 해커톤 규모에서 절대점수가 실무적으로 얼마나 골치아픈지 시사하는 방증이다. HACKMAN 규모(소~중형 교내/기업 공모전)에서는 절대점수가 여전히 합리적 선택일 수 있지만, 팀 수·심사위원 수가 커질 경우 이 문제를 재검토할 필요가 있다.
- **CTFd의 스코어보드 쿼리 자체 최적화** — HACKMAN은 캐시/ETag로 부하를 줄이지만, DB 쿼리 자체가 느리면 캐시 미스 시(3초 캐시 만료 직후 동시 요청 등) 여전히 병목이 될 수 있다. CTFd처럼 스코어보드 집계 쿼리 자체의 성능을 별도로 점검해볼 가치가 있다.
- **DoraHacks의 "BUIDL AI" 자동 리뷰/스마트 스코어링** — HACKMAN이 계획 중인 "LLM 사전분석(구조적 발견만 제시, 점수는 안 줌)"과 목적은 비슷하지만 DoraHacks는 이미 "스마트 점수"까지 자동 생성한다고 광고한다. HACKMAN이 점수를 주지 않고 구조적 발견만 주는 방향(앵커링 편향 회피)으로 가는 건 DoraHacks보다 신중한 설계로 보이며, 이 차별점을 문서화해둘 가치가 있다.
- **ScoreJudge의 심사위원별 독립 링크(공유 편집 없음)** — 여러 심사위원이 같은 화면/토큰을 공유하다 실수로 서로 점수를 덮어쓰는 사고를 막는 간단하지만 실용적인 설계다. HACKMAN의 "심사위원별 upsert(재저장 시 덮어씀)" 구조와 맞물려, 심사위원 인증/세션 분리가 확실한지 다시 점검할 이유가 된다.
- **dribdat의 다양한 외부 도구 연동(Git/Forgejo/Etherpad 진행 로그 자동 수집)** — 참가자가 수동으로 제출 상태를 업데이트하지 않아도 실제 커밋 활동으로 진행 상황을 유추하는 아이디어. HACKMAN의 GitHub 연동(README/파일트리 조회)을 한 단계 더 활용해 "최근 커밋 활동" 같은 신호를 팀 카드나 심사 화면에 노출하는 것도 검토해볼 만하다.

## 6. 검증하지 못한 것 / 확인 필요

- **정확한 "최근 커밋 날짜"**: Gavel, dribdat, JunctionApp 모두 WebFetch로 가져온 GitHub 페이지에서 총 커밋 수는 확인했지만 최신 커밋의 정확한 날짜/상대시간(예: "3일 전")은 렌더링된 텍스트에서 추출하지 못했다. 실제 유지보수 활성도를 판단하려면 `git log -1` 또는 GitHub API(`/repos/{owner}/{repo}/commits?per_page=1`)로 직접 재확인이 필요하다.
- **Unstop**: 공식 사이트가 쿠키 관련 오류 페이지만 반환해 조직 대시보드/심사 기능을 직접 확인하지 못했다. 검색 스니펫 수준의 정보만으로 표에 넣었다 — 재검증 필요.
- **Taikai**: 심사/스코어링/팀 매칭의 구체적 동작 방식이 마케팅 페이지에는 나오지 않았다. 공식 문서(docs.taikai.network 등)가 있다면 별도로 확인해야 한다.
- **DoraHacks**: dorahacks.io 메인 페이지가 WebFetch에서 HTTP 405를 반환해 직접 확인하지 못했고, 블로그/미디엄 글로만 기능을 재구성했다. "BUIDL AI"의 실제 채점 방식(절대점수인지 다른 방식인지)은 확인 못했다.
- **Match&Hack, FocusFlow(sahil-verma-9696)**: 둘 다 사실상 활동이 멈췄거나(Match&Hack: 2023~2024년 이후 커밋 없음, 스타 0~1) 유지보수 여부가 불확실한(FocusFlow: 해커톤 출품작, 이슈/PR 0건) 소규모 프로젝트다. 참고용으로만 표에 넣었고, 실사용 사례로 인용하기엔 근거가 약하다.
- **MLH(Major League Hacking)**: "MLH 심사는 자원봉사 멘토가 진행한다"는 설명만 확인했고, MLH가 공개한 별도의 심사/팀매칭 오픈소스 도구는 이번 조사에서 찾지 못했다. 존재하지 않는 것인지 조사가 부족한 것인지 단정할 수 없다.
- **bherrmann7/judge의 라이선스**: "Creative Commons"라고만 표시되어 있고 정확한 버전(CC-BY? CC0?)은 레포 페이지에서 확인하지 못했다.
- **MLH/HackAssist류의 "hackathon-starter" 인접 판정 도구**: 프롬프트에서 요청된 "HackAssist"라는 이름의 프로젝트는 검색에서 신뢰할 만한 결과를 찾지 못했다. 존재 여부 자체를 확인하지 못했으므로 표에 넣지 않았다.
- **DACON의 정확한 채점 흐름**: 팀 수 통계(252,660+)는 확인했지만, 이게 코드 제출 자동채점 대회에 한정된 것인지 정성평가가 포함된 대회도 있는지는 랜딩 페이지만으로 구분하지 못했다.
