## 2. 제약이 후보를 먼저 거른다

이 장이 나머지 전부를 결정한다. 아이디어의 매력도가 아니라 **운영 제약**이 후보를 거른다.

- **gunicorn 워커가 1개다.** `backend/Procfile` 에 `-w` 가 없다. 한 요청이 멈추면 그동안
  서비스 전체가 멈춘다 — 5초마다 도는 스코어보드 폴링까지 전부 타임아웃 난다.
- **배경 실행 수단이 없다.** Celery·RQ 가 없고, 붙이면 인프라가 하나 늘어난다.
- **Render Free 는 15분 미사용 시 잠든다.** 첫 요청에 30~50초(`DEVELOPMENT.md` 아키텍처
  드라이버 표). 재배포에도 같은 콜드 스타트가 따라붙어, 대회 당일에 코드를 고치는 것은 선택지가
  아니다.
- **이미 한 번 겪었다.** NVIDIA build API 가 응답 바이트를 하나도 안 보내고 무기한 멈추는 일이
  있었고(`DEVELOPMENT.md` 트러블슈팅, 2026-09-08), 그 결과로 모든 제공사 호출에 30초 타임아웃이
  걸렸다(`backend/contests/llm/base.py:47-50`). 타임아웃은 사고를 30초로 줄일 뿐 없애지 않는다.

**따라서 AI 는 대회 당일 요청 경로에 들어갈 수 없다.** 들어갈 수 있는 자리는 셋뿐이다:

| 자리 | 성격 | 지금 여기 있는 것 |
|---|---|---|
| (a) 참가자당 1회, 짧은 입력 | 대회 전, 사람 한 명이 자기 차례에 한 번 | 프로필 태그 추출 |
| (b) 운영자가 심사 전에 누르는 일괄 실행 | 대회 당일이지만 심사 시작 **전**, 운영자가 시점을 고름 | (비어 있음 — 1순위 후보) |
| (c) 대회 종료 후 | 시간 압박 0, 워커 경합 0 | (비어 있음 — 2순위 후보) |

이 표 밖의 AI 아이디어는 전부 탈락이다. 순위를 매기기 전에 이 필터가 후보 절반을 먼저 거른다.
아래 5장의 순위도 "가치"보다 이 적합성을 먼저 본 결과다.

## 3. 지금 AI 가 하는 일 / 안 하는 일

**하는 일 — 딱 하나다.**

`backend/contests/profile_extract.py` — 참가자가 쓴 자기소개 한 문단을 기술 스택·관심 분야·
역할·숙련도 태그로 바꾼다. 자리 (a)에 정확히 들어맞는다: 참가자당 1회, 짧은 입력, 작은 JSON 출력.
결과는 참가자가 직접 고칠 수 있고(`Profile` 은 원문과 추출 결과를 **둘 다** 보관한다),
실패해도 예외를 밖으로 내보내지 않아 팀빌딩 화면이 막히지 않는다.

`backend/contests/llm/base.py` — Anthropic·OpenAI·Google 세 제공사 어댑터. SDK 는 지연 임포트,
키가 설정된 제공사만 `available_models()` 로 노출, 호출당 30초 타임아웃. 제공사별로 다른 것은
"요청을 보내고 텍스트·토큰 수를 돌려주는" 함수 하나뿐이고 프롬프트 구성·JSON 파싱은 공용이다 —
**모델을 바꿔도 프롬프트 비교가 아니라 모델 비교가 된다.** 5장 4순위(모델 비교 실험)가
가능한 이유가 이 구조다.

**의도적으로 안 하는 일.**

`backend/contests/matching.py:1-12` — 팀 추천 **순위는 전부 규칙 기반이다.** 기각 근거가 파일
머리에 이미 적혀 있다: (1) 결정적이고 설명 가능해야 한다("왜 나는 저 팀에 못 갔나"에 운영자가
답할 수 있어야 한다), (2) 추천은 화면을 열 때마다 다시 계산되는데 매번 LLM 을 부르면 워커 1개짜리
서버가 막힌다. **추출은 참가자당 1회, 매칭은 매번** — 이 분담이 2장의 제약과 정확히 맞물린다.

조사 §4 도 HACKMAN 의 차별점으로 "LLM 랭킹"이 아니라 **"LLM 태그 추출 + 규칙 기반 점수의 결합"**
을 지목했다. 즉 지금의 분담 자체가 차별점이고, LLM 을 순위로 밀어 넣으면 그 차별점이 사라진다.

## 4. 경쟁 제품은 AI 로 무엇을 하나

전부 조사 문서 인용이다. 새로 확인한 것은 없다.

| 제품 | AI 로 하는 것 | 출처 / 신뢰도 |
|---|---|---|
| DoraHacks (BUIDL AI) | AI 기반 자동 리뷰 + 표절 검사 + **스마트 스코어링**(점수까지 자동 생성한다고 광고) | 조사 §2-1, §5. **단, 조사 §6 이 "메인 페이지 HTTP 405 로 직접 확인 못 하고 블로그·미디엄으로 재구성"이라고 명시했다.** 실제 채점 방식은 미확인 |
| HackerEarth | 표절 탐지, 심사자 콘솔의 점수+코멘트 통합 뷰, 감사 로그 | 조사 §2-1 |
| DevMatch | GitHub 프로필 데이터로 팀원 추천(팔로워비·커밋빈도·언어로 프론트/백 판별) — **LLM 이 아니라 TensorFlow Lite 자체 모델** | 조사 §2-3 |
| Devpost | **없음.** 역할·스킬 태그로 필터링한 목록을 사람이 직접 훑는 방식, 추천 알고리즘 자체가 없다 | 조사 §2-3 |
| FocusFlow | 자동 발표자료 생성을 **자칭** | 조사 §2-3, §6. 해커톤 출품작이고 이슈·PR 0건이라 조사 문서가 "신뢰도 낮게 취급할 것"으로 표시 |

**여기서 읽을 것 두 가지.**

1. **저장소 자동 분석은 이미 상용화돼 있다(DoraHacks).** 아이디어가 검증됐다는 뜻이고, 동시에
   HACKMAN 만의 것이 아니라는 뜻이다. 조사 §5 는 HACKMAN 이 점수를 주지 않고 구조적 발견만
   제시하는 방향을 "DoraHacks 보다 신중한 설계"로 평가했다 — 차별점은 기능의 유무가 아니라
   **점수를 주지 않는다는 선택**에 있다.
2. **팀 매칭에 LLM 을 쓰는 곳은 조사 범위에서 하나도 없었다.** Devpost 는 알고리즘 자체가 없고
   DevMatch 는 LLM 이 아니다. HACKMAN 의 조합이 실제로 드물다는 조사 §4 의 판단이 여기서 재확인된다.

**조사 범위에서 언급이 없는 것: 심사 결과를 참가자에게 피드백으로 돌려주는 기능.**
조사 §2 의 비교표 어느 칸(겹치는 기능/없는 기능)에도 이 항목이 나오지 않는다. 다만 조사가
그 축으로 제품을 훑지 않았을 가능성이 있으므로 **"경쟁 제품에 없다"가 아니라 "조사 범위 내에서
언급 없음"으로 다룬다.** 5장 2순위를 "빈 시장"이 아니라 "우리 참가자의 실제 결핍"을 근거로
올린 이유다.

## 5. 후보별 판정

### 1순위 — 심사 보조: 제출 저장소 사전 분석 (착수 권고)

기획은 `DEVELOPMENT.md` 의 「다음 작업」에 이미 확정돼 있다. 이 검토가 더하는 것은 **착수
판정**이다.

- **가치:** 심사위원은 팀당 10분 안에 저장소를 다 읽을 수 없어 사실상 README 와 데모 링크만 보고
  점수를 매기게 된다. 심사 품질이 곧 대회 품질인데 여기가 가장 얇다.
- **제약 적합성:** 자리 (b). 운영자가 심사 **전에** 한 번 누르는 일괄 엔드포인트로 처리하면
  워커 블로킹도, 새 인프라도 없다. 대회 당일 요청 경로에 LLM 이 들어가지 않는다.
- **인프라는 이미 있다.** `backend/contests/github.py` 의 프록시 네 종(`repo`/`readme`/`tree`/`file`)
  + 30분 캐시 + 토큰으로 시간당 5000회. `llm/base.py` 의 3사 어댑터. **없는 것은 "읽은 내용을
  요약해 심사위원 앞에 놓는 단계"뿐이다.**
- **Anthropic 키 확보가 판정을 바꾼다.** `DEVELOPMENT.md` 는 이 작업이 "낯선 코드 50k 토큰을 읽고
  주장과 실제를 대조하는" 일이라 저가 모델이 무너지는 지점이고, 실패 방식이 고약하다고 적었다 —
  README 를 그럴듯하게 요약해 돌려주면 심사위원이 이미 스스로 할 수 있는 일이라 기능이 있으나
  마나가 된다. **검증된 모델이 `gemini-3.5-flash` 하나뿐인 동안에는 이 위험이 착수를 막을 이유였고,
  지금은 아니다.**
- **점수는 제안하지 않는다** — 4장에서 본 대로 이것이 DoraHacks 대비 유일한 설계 차별점이다.
  유지 권고.
- **규모:** 모델 1(`SubmissionReview`) + 마이그레이션 + `judge_assist.py` + 엔드포인트 3 +
  `SubmissionReview.tsx` 패널. 후보 중 가장 크다.

### 2순위 — 심사 코멘트 → 참가자 피드백 다이제스트 (신규 제안, 착수 권고)

**지금 참가자는 등수만 받고 끝난다.** `Score.comment` 는 작성한 심사위원 본인과 staff 만 볼 수
있다 — `backend/contests/views.py:396-400` 이 staff 가 아니면 `judge__user=self.request.user` 로
큐리셋을 좁히므로, 참가자에게는 애초에 조회 경로가 없다. 교내·동아리 대회에서 참가자가 가장
아쉬워하는 지점이 여기다. 심사위원들은 이미 코멘트를 썼는데 그게 아무에게도 안 간다.

- **제약 적합성이 후보 중 가장 좋다.** 자리 (c) — 대회가 **종료** 상태로 넘어간 뒤 실행한다.
  워커 경합 0, 콜드 스타트 무관, 시간 압박 0. 실패하면 그냥 다시 누르면 된다.
- **비용이 사실상 없다.** 20팀 × (심사위원 몇 명의 짧은 코멘트) = 입력 수천 토큰 수준.
  1순위의 저장소 50k 토큰과는 두 자릿수 차이다.
- **규모가 작다.** 모델 1 + 엔드포인트 2(운영자 생성 / 참가자 조회) + 화면 1. 1순위의 몇 분의 1.
- **착수 전 운영 판단이 하나 필요하다 — 코드 문제가 아니다.**
  (1) 참가자에게 심사위원별 코멘트 원문을 보여줄지, 종합 요약만 보여줄지.
  (2) 운영자 검토 게이트를 둘지(생성 → 운영자가 읽고 → 공개). **권고: 요약만 + 운영자 게이트.**
  원문 공개는 특정 심사위원이 누구 말을 했는지 역추적되는 순간 다음 대회 심사위원 섭외가 어려워진다.
  결선 점수를 시상 전까지 감추는 것과 같은 등급으로 다루는 것이 일관적이다.

### 3순위 — 정규 스택 목록: 이미 돌고 있는 AI 출력의 품질 수리

기획은 `DEVELOPMENT.md` 의 「기술 스택 입력: 자유 타이핑 → 정규 목록에서 다중 선택」에 확정돼 있다.
이 검토가 더하는 것은 **분류**다: 이건 새 AI 기능이 아니라 **이미 배포돼 돌고 있는 AI 출력의
품질 문제**다.

`react` / `리액트` / `React.js` 가 전부 다른 스택으로 세어진다. `matching.py` 의 `_normalize()` 는
대소문자와 앞뒤 공백만 없애므로 이 차이를 못 잡는다. 결과로 `WEIGHT_SKILL_SPREAD`(스택이 덜
겹치는지)가 실제로는 "표기가 다른지"를 재게 된다. **틀렸다는 신호가 어디에도 안 나타나는 게 특히
나쁘다.**

순서 논리로 3위다 — 새 AI 를 붙이기 전에 붙어 있는 AI 의 출력이 쓸 만해야 한다. 그런데 2위보다
뒤인 이유는 규모다: 모델 + 마이그레이션 + CRUD API + 운영자 관리 화면 + 시드 데이터 + 기존
데이터 일회성 정리가 한꺼번에 따라온다. 참고로 매칭에서 스택의 비중은 100점 중 10점이고 역할은
45점이라, **이 작업은 매칭 정확도보다 운영자의 손이 묶이지 않게 하려는 것**이라는 원래 판단이
여전히 맞다.

### 4순위 — 모델 비교 실험 (1·2 착수 전 사전 작업)

Anthropic 키가 들어오면 **저장소 분석부터 시작하지 말고 프로필 추출부터 재실행한다.** 이유:

- 입력이 짧고 정답이 명확해(자기소개에 실제로 적힌 것만 뽑았는가) 사람이 몇 분 만에 판정할 수 있다.
- `Profile.extracted_by` 에 어느 모델이 뽑았는지 이미 기록된다(`backend/contests/models.py:183-184`).
  재추출 대상 선별과 결과 대조가 스크립트 없이 된다.
- 프롬프트 구성·파싱이 공용이라(`llm/base.py`) 프롬프트 비교가 아니라 진짜 모델 비교가 된다.
- 비용이 몇 센트다.

그 다음 실제 제출 저장소 3~5개로 1순위의 분석 품질을 비교한다. 이 실험 결과로 기본 모델을 정한다.

## 6. AI 가 답이 아닌 것

이 장이 이 검토의 나머지 절반이다. "AI 를 어디에 쓸까"만 적고 끝내면, 정작 비용 대비 효과가 가장
큰 항목을 놓친다.

### 6-1. 심사위원 간 점수 편차 — 통계로 푼다 (AI 아님, 반나절, 최고 가성비)

조사 §5 가 짚은 HACKMAN 의 가장 큰 설계 약점이다. 지금은 심사위원별 절대점수를 그냥 평균 낸다.
어떤 심사위원은 전체적으로 후하고 어떤 심사위원은 박한데, 이 편차가 그대로 순위에 실린다.

조사가 보여준 선택지는 셋이다:

1. **Gavel 의 페어와이즈(Crowd-BT)로 전환** (조사 §3) — 상대 비교라 캘리브레이션 문제가 원천적으로
   없다. 하지만 결과가 "순위"이지 "몇 점"이 아니라 시상 등급 컷을 점수로 설명하기 어렵고, 비교가
   끝나기 전까지 랭킹이 불안정해 **실시간 스코어보드를 프로젝터에 띄우는 HACKMAN 의 운영 방식과
   정면으로 충돌한다.** 채택하지 않는다.
2. **ScoreJudge 의 outlier drop** (조사 §2-4, §5) — 최고점·최저점 자동 제외. 구현이 가장 싸다.
3. **심사위원별 z-score 정규화** — 심사위원의 평균·표준편차로 정규화한 뒤 합산. 보정력은 더 좋지만
   심사위원 수가 적으면(3~4명) 표본이 모자라 오히려 불안정해진다.

**권고: 2번(outlier drop)을 심사위원 5명 이상일 때만 적용.** 스코어보드 집계 한 곳만 고치면 되고,
반나절이면 끝나며, 참가자에게 "최고·최저 점수는 빼고 계산합니다"라고 설명하기도 쉽다.
조사 §2-2 가 남긴 방증도 무시할 게 아니다 — 핀란드 Junction 이 실제 대형 해커톤을 운영하면서
절대점수 대신 Gavel 의 페어와이즈를 택했다. 지금 규모에서는 절대점수가 여전히 맞는 선택이지만,
**팀 수·심사위원 수가 커지면 이 항목을 다시 열어야 한다.**

**확인 결과 (2026-09-11): 적용 불가.** 실제 평균 심사위원 수가 **3~4명**이라 위 권고의 전제
(5명 이상)를 못 채운다 — 8장이 "적용 대상이 아예 없을 수도 있다"고 단 단서가 그대로 나왔다.
3~4명에서 최고·최저를 빼면 남는 표본이 한둘이라 평균이 더 흔들리고, z-score 도 같은 표본 부족
문제에 걸린다. **이 검토가 "비용 대비 효과가 가장 크다"고 꼽았던 항목은 지금 규모에서는 착수
불가다** (`DEVELOPMENT.md` 「보류 중」으로 이동, 재검토 조건은 심사위원 5명 이상).

남는 답은 사후 보정이 아니라 **채점 전에 기준을 맞추는 쪽**이다 — 공통 루브릭과 예시 채점을
심사 시작 전에 공유하는 방식. 표본이 적을수록 사후 통계 보정은 약해지고 사전 합의가 강해진다.
다만 루브릭 모델이 없어(6-6) 지금은 기능이 아니라 운영 수칙이고, 이 검토는 여기까지만 적는다.
**편차라는 약점 자체는 해소되지 않은 채 남는다.**

### 6-2. 표절·중복 탐지 — 첫 커밋 시각으로 푼다 (AI 아님, 반나절)

HackerEarth 와 DoraHacks 엔 있고 HACKMAN 엔 없다(조사 §2-1). 하지만 그대로 따라갈 항목이 아니다.

- **진짜 코드 표절 탐지는 LLM 의 일이 아니다.** MOSS·JPlag 계열의 토큰 지문 비교가 하는 일이고,
  LLM 에게 "이거 표절인가" 물어보는 것은 신뢰할 만한 판정을 주지 않는다.
- **오탐의 대가가 다르다.** 팀 추천이 틀리면 "추천이 별로네"로 끝나지만, 표절 판정이 틀리면
  참가자에게 부정행위 혐의를 씌우는 것이다. 사람이 검토하지 않는 자동 표절 판정은 권하지 않는다.
- **교내 대회에서 실제로 잡고 싶은 것은 다른 문제다:** "대회 시작 전에 이미 만들어 둔 프로젝트를
  냈는가". 이건 **저장소의 첫 커밋 시각이 `Contest.start_at` 보다 이른지** 보면 잡힌다.
  `backend/contests/github.py` 에 프록시·캐시·토큰 처리가 이미 있어 커밋 목록 조회를 하나 더
  붙이는 일이다. AI 없이 반나절이고, 결과가 "혐의"가 아니라 **확인 가능한 사실**(첫 커밋 시각)이라
  심사위원이 직접 판단할 수 있다.

### 6-3. LLM 을 팀 매칭 순위에 넣기 — 재검토 불필요

`backend/contests/matching.py:1-12` 가 이미 기각했고 근거(결정성·설명 가능성·워커 블로킹)가 전부
여전히 유효하다. 조사 §4 도 차별점으로 지목한 것은 "규칙 기반 점수 **+** LLM 태그 추출의 결합"이지
LLM 랭킹이 아니다. **이 항목은 다시 열지 않는다.**

### 6-4. AI 자동 채점 / 점수 제안 — 유지 기각

DoraHacks 는 "스마트 스코어링"까지 광고한다(조사 §2-1, 단 §6 이 실제 방식 미확인으로 표시).
HACKMAN 은 하지 않는다 — 제안 점수를 띄우면 심사위원이 거기에 닻을 내려 결국 모델이 채점하는 것과
같아진다. 대회의 정당성이 걸린 부분이고, 이미 내려진 판단(`DEVELOPMENT.md` 「점수를 대신 매기지
않는 이유」)이다. **이 검토도 유지 권고한다.** 4장에서 본 대로 이것이 오히려 차별점이다.

### 6-5. 자동 발표자료 생성 — 기각

FocusFlow 가 자칭한 기능인데(조사 §2-3), 조사 §6 이 그 프로젝트 자체를 "이슈·PR 0건, 신뢰도 낮게
취급할 것"으로 표시했다. 그와 별개로 참가자는 이미 자기 발표 자료를 만들고, 만드는 과정 자체가
해커톤의 일부다. 기각.

### 6-6. 대회 설명 → 심사 루브릭 초안 — 보류 (선행 기능 없음)

운영자가 쓴 대회 설명에서 심사 항목을 뽑아 주는 아이디어는 매력적이지만, **HACKMAN 에는 루브릭
모델 자체가 없다.** `Score.value` 는 단일 0~100 점수 하나다(`backend/contests/models.py:109-112`).
항목별 배점 구조를 먼저 만들어야 하고, 그건 AI 작업이 아니라 도메인 모델 변경이다.
루브릭 기능을 하게 되면 그때 다시 연다.

## 7. 착수 전 남은 확인

- **Anthropic 키:** 발급 → Render 환경변수 `ANTHROPIC_API_KEY` 등록 → `backend/requirements.txt` 에
  `anthropic` 추가(현재는 `google-genai`·`openai` 만 있고 anthropic 은 "쓸 때 추가한다"로 비어 있다).
  키를 넣으면 `available_models()` 가 자동으로 선택지에 올리므로 프론트 변경은 없다.
- **2순위의 공개 범위** — 요약만 vs 원문, 운영자 게이트 유무. 코드 문제가 아니라 운영 판단이라
  착수 전에 정해야 한다(5장 2순위 권고 참고).
- **1순위 1차에서 Batch API 를 쓸지** — 3사의 Batch·비동기 방식이 제각각이라 1차는 **운영자 트리거
  + 순차 실행**을 권고한다. Batch 는 팀 수가 늘어 순차 실행이 실제로 느려질 때 연다.
- **완료를 무엇으로 확인할지** — 운영자가 화면에서 새로고침할지, 기존 폴링에 진행 상태를 실어
  보낼지. 스코어보드 폴링이 이미 있으므로 후자가 자연스럽지만, 폴링 페이로드가 커지는 대가가 있다.

## 8. 이번 검토에서 확인하지 못한 것

- **DoraHacks BUIDL AI 의 실제 동작.** 조사 §6 이 이미 "메인 페이지 HTTP 405 로 직접 확인 못 함,
  블로그·미디엄으로 재구성"이라고 적었다. 이 검토도 그 한계를 그대로 물려받는다 — "DoraHacks 가
  이미 한다"는 서술은 마케팅 주장 수준의 근거다.
- **"참가자 피드백을 돌려주는 경쟁 제품이 없다"는 부재 증명.** 조사 §2 표에 그 축의 칸이 없을 뿐,
  없다고 확인한 것이 아니다(4장 말미 참고).
- **`gemini-3.5-flash` 의 실제 추출 품질.** 지금 프로덕션에서 돌고 있지만 다른 모델과 나란히 놓고
  비교한 적이 없다. 5장 4순위가 바로 그 실험이다 — **이 검토의 순위는 그 실험 결과에 따라 바뀔 수
  있다.**
- **실사용 규모 — 확인됨 (2026-09-11).** 심사위원이 실제로 몇 명인지에 따라 6-1 의 권고(outlier
  drop 을 5명 이상일 때)가 적용 대상이 아예 없을 수도 있다고 적었는데, 실제 평균이 **3~4명**으로
  확인되어 그대로 됐다. 6-1 에 후속 판정을 반영했다.
