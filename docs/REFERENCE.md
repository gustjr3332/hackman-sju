## 컨셉

마케팅 랜딩이 아니라 "라이브 운영 데스크". 대회 생성 → 팀 구성 → 심사위원 채점 → 실시간
스코어보드 → 시상으로 이어지는, 시간에 쫓기며 숫자를 계속 확인하는 도구. 스코어보드가
페이지의 무게중심이며, 리스트 맨 아래 부록이 되면 안 된다.

예외는 대회 목록 화면 하나다. 여기는 로그인하지 않은 관람자가 처음 닿는 자리라 여백을 크게
두고 진입 배너를 얹는다. 대회 안으로 들어간 뒤(상세·심사·팀빌딩·시상)는 다시 밀도 우선이다.

문서·코드를 다루는 도구답게 GitHub 계열의 밀도 있는 정보 배치를 참고한다 — 상단 브레드크럼
바, 밑줄 탭, 행 hover, 파일트리 + 라인번호 코드 뷰. 단, 색과 서체는 아래 토큰을 벗어나지
않는다.

## 색상

라이트가 기준이고, 다크는 같은 색상(hue)에서 명도만 올린다. 실제 값은
`frontend/src/style.css`의 `:root` / `[data-theme='dark']`에 있다.

| 토큰 | 라이트 | 다크 | 용도 |
|---|---|---|---|
| `--ink` | `#17181D` | `#EEEFF1` | 본문·제목 |
| `--paper` | `#F4F5F3` | `#121316` | 배경 |
| `--paper-raised` | `#FFFFFF` | `#1C1D22` | 행 hover, 보조 면 |
| `--surface` | `#FFFFFF` | `#1C1D22` | 카드·입력창·패널 바닥 |
| `--line` | `#E3E4E0` | `#2C2E34` | 헤어라인 |
| `--live` | `#1F7A55` | `#46B886` | 모집중·진행중, LIVE 신호 |
| `--judging` | `#C4622A` | `#E08148` | 심사중, 마감 임박 경고 |
| `--signal` | `#2A55C4` | `#7B9CF0` | 점수·순위 등 데이터 강조 (코발트) |
| `--muted` | `#5F636C` | `#A3A6AE` | 보조 텍스트 |
| `--hero-bg` / `-ink` / `-muted` | `#17181D` / `#F4F5F3` / `#B8BBC2` | `#262830` / `#EEEFF1` / `#A3A6AE` | 진행 중 대회·카운트다운 히어로 카드 |

- 채도는 "지금 라이브"일 때만 쓴다. 나머지는 그레이/잉크 톤.
- 크림+테라코타(`#D97757` 계열), 인디고(`#4F46E5`, Tailwind 기본값), 그라디언트 배경은 쓰지 않는다.
- 시상식 무대는 프로젝터 화면이므로 **테마와 무관하게 어두운 배경 고정**(`#14181c` 바닥 /
  `#f3f4f1` 글자). 이때 액센트는 다크 값(`#3FA372`·`#E08148`·`#6C93C7`)을 쓴다.

## 타이포그래피

**Pretendard 한 서체**(npm `pretendard`, 번들에 포함 — 오프라인·앱에서도 같다). 한글·라틴·숫자가
한 가족이라 OS 서체로 떨어지는 글자가 없다. 숫자 정렬은 모노 서체 대신 `body`의
`font-variant-numeric: tabular-nums`로 맞춰 스코어보드가 전광판처럼 읽힌다. `--font-mono`는
`--font-ui`와 같은 값으로 남겨 두었다(숫자 자리 표시용 이름).

### 타입 스케일

기준 크기는 `:root { font-size: 19px }`가 전체 스케일 레버이고, 개별 값은 전부 `rem`으로
적는다 — 화면마다 px를 직접 박지 않는다.

| 역할 | rem | 실제 크기 |
|---|---|---|
| 화면 제목 | `1.6rem` | 약 30px |
| 섹션 제목 | `1.05rem` | 약 20px |
| 본문·리스트 항목 | `0.9rem` | 약 17px |
| 보조 텍스트·메타 | `0.82rem` | 약 16px |
| 캡션 | `0.75rem` | 약 14px |
| 스코어보드 숫자 | `1.1rem` 이상 | 21px 이상 |

프로젝터에 띄우는 시상식 화면은 `clamp()`로 더 크게 간다(상 이름 최대 4rem, 팀 이름 최대 3rem).

## 레이아웃

- **상단 바** — 높이 68px, 아래에 헤어라인 1px. 왼쪽에 로고 마크(28px 잉크 사각형 + 모노 `H`)
  와 워드마크, 그다음 `/` 구분자로 브레드크럼(대회명 → 화면명). 오른쪽에 테마 토글과 로그인
  버튼/계정(로그인 폼은 기본 숨김, 버튼을 눌러야 편다).
- **본문** — 컨테이너 최대 폭 1080px, 화면 가운데 배치하되 **안의 내용은 전부 좌측 정렬**한다
  (가운데 정렬된 텍스트·카드는 쓰지 않는다).
- **대회 목록** — 맨 위에 대회 이름 검색창(입력 44px), 그 아래 상태 필터 칩, 그 아래
  3열 카드 그리드(`repeat(3, minmax(0, 1fr))`, gap 24px). 카드는 `--surface` 바닥 + 헤어라인
  테두리, 라운드 14px, **그림자 없음**. **진행 중 대회는 어두운 히어로 카드**(`--hero-bg`).
  카드 안은 `상태 칩 → 대회명 → 한 줄 설명 → (헤어라인) → 메타(기간·팀 수)` 순서로 쌓고,
  메타는 카드 아래에 붙도록 그 위를 `margin-top: auto`로 민다. 종료된 대회는 135° 빗금
  배경(`--paper-raised`/`--paper` 6px 간격)으로 비활성을 드러낸다.
- **그 외 리스트** — 카드로 만들지 않는다. 헤어라인으로 구분한 행, 행 hover 시
  `--paper-raised`. 팀빌딩 추천처럼 항목마다 점수·근거·행동이 함께 붙는 목록만 카드를 쓴다.
- **상태 표시** — **알약 칩**(글자색 + 같은 색 12% 바탕, 굵게). 종료는 빗금 패턴으로 비활성임을
  드러낸다. 경고·안내 문구(오프라인, 잠금 사유 등)만 왼쪽 컬러 레일을 쓴다.
- **탭** — 칩(테두리 + 알약, 활성은 잉크 바탕 + 페이퍼 글자).
- **카운트다운** — 어두운 히어로 카드 안에 시간·분·초 타일.
- **스코어보드** — 상세 화면 최상단, 14px 카드. 숫자는 우측 정렬 + tabular. 순위는 동점 공동 순위(1, 1, 3),
  점수 없는 팀은 순위 없이 맨 아래.
- **코드 열람** — 왼쪽 파일트리(모노) + 오른쪽 라인번호 코드 뷰. 문법 하이라이팅은 범위 밖.
- **제출물 갤러리** — 대회 목록과 같은 카드 규칙의 3열 타일. 타일 안은
  `팀 이름 + 점수(모노, 우측) → 제출물 제목 → 한 줄 설명 → (헤어라인) → 데모·코드 표시`.
  점수는 `--signal`, 제출하지 않은 팀은 흐리게 두고 "미제출"을 쓴다.
  라운드는 칩 탭이고 결선 탭은 스코어보드와 같은 권한으로만 보인다.
- **프로젝트 상세** — 본문 컬럼(소개 → 데모 → 코드) + 오른쪽 240px 사이드(팀원·리포지토리·
  데모 링크). 좁은 화면에서는 사이드가 본문 아래로 내려간다. 머리에는 점수를 모노로 크게 둔다.

## 컨트롤 규격

- 누를 수 있는 요소의 최소 높이는 **44px**(모바일 탭 타깃). 아이콘 버튼은 36px 정사각이고
  라벨을 붙이지 않는다 — 뜻이 그림만으로 통하지 않으면 아이콘 버튼으로 만들지 않는다.
- 헤더 우측 사용자 표시는 **원형 이니셜 아바타(30px) + 이름/역할 2줄**(좁은 화면은 아바타만,
  눌러서 계정 메뉴).
- 입력창 높이 44px, 좌우 패딩 12px. **라운드는 세 가지만**: 컨트롤(버튼·입력) 10px(`--r`),
  면(카드·패널) 14px(`--r-card`), 칩·아바타는 알약/원형. 로고 마크만 앱 아이콘과 같은 6px.
- 1차 버튼은 잉크 배경 + 페이퍼 글자. 2차 버튼은 라인 테두리 + 투명 배경.
- 비활성 버튼은 `opacity: .5` + `cursor: not-allowed`로, 왜 잠겼는지 옆에 한 줄로 알린다.

## 아이콘 · 모션

- 아이콘은 **인라인 SVG만** 쓴다(스트로크 1.4px, 16/20/24px 그리드). 이모지·딩벳 문자는
  콘텐츠에도 UI에도 쓰지 않는다.
- 모션은 상태 변화를 알릴 때만 쓴다:
  - `LIVE` 표시의 느린 점멸(1.6s)
  - 시상식 **수상팀 공개** 시 컨페티 낙하 + 링 확산 + 수상 정보 상승
  - 그 외 화면 전환·hover에 애니메이션을 붙이지 않는다.
- 컨페티 색은 팔레트(`live`/`judging`/`signal`/`paper`)만 쓴다. 무지개색 금지.

## 화면별 기준

| 화면 | 핵심 |
|---|---|
| 대회 목록 | 기본 화면. 검색창(이름 포함 검색, 서버 요청 없음), 상태 필터 밑줄 탭, 3열 카드 그리드. 로그인 폼은 기본 숨김, 헤더 "로그인" 버튼으로만 연다. 운영자에게만 `+ 새 대회 만들기` |
| 대회 상세 | 스코어보드가 히어로. 상단에 상태 스테퍼(현재 단계만 비활성, 나머지는 자유 전환) + 진행중일 때 카운트다운 |
| 심사하기 | 팀별 접이식 행. 펼치면 채점 폼 + 웹 데모/코드 탭. 심사중이 아니면 폼 잠금 + 사유 표시 |
| 제출물 갤러리 | `/c/:slug/gallery`. 로그인 없이 공개. 점수는 예선만, 결선은 운영자·배정 심사위원에게만. 심사 보조 분석은 여기에 붙이지 않는다 |
| 프로젝트 상세 | `/c/:slug/projects/:teamId`. 데모 iframe·코드 열람·첫 커밋 시각은 심사 도구의 패널을 그대로 쓴다 |
| 로그인 | 좁은 단일 컬럼. 아이디 또는 이메일로 로그인, 회원가입은 아이디+이메일+비밀번호. 8자 미만·확인 불일치는 입력 즉시 안내 |
| 시상식 | 어두운 무대 고정. 낮은 등수부터 → 대상. `상 이름 공개 → 수상팀 공개 → 다음 시상`. 해당 등수 팀이 없으면 "순위 정보 없음" |

# 2. 설계 결정 기록

## 2.1 Django+Render → Supabase 네이티브 전환 (2026-09)

**왜:** Render 무료/저가 인스턴스는 gunicorn 워커 1개라 콜드 스타트(15분 미사용 시 슬립,
첫 요청 30~50초)와 "한 요청이 멈추면 서비스 전체가 멈춘다"는 제약이 거의 모든 설계 판단을
지배하고 있었다. Supabase는 이미 DB로 쓰고 있었으므로, REST·인증·실시간·서버리스 함수까지
같은 플랫폼으로 옮기면 이 제약 자체가 없어진다.

**무엇으로 바꿨나:**

| 예전 (Django+Render) | 지금 (Supabase) |
|---|---|
| DRF 뷰 + 커스텀 권한 클래스 | Postgres RLS 정책 + RPC 함수 |
| `*_STATUSES` 딕셔너리 검사 (views.py) | BEFORE 트리거가 한국어 예외 발생 |
| simplejwt, `auth_user` 커스텀 해시 | Supabase Auth (`auth.users`, GoTrue) |
| 5초 REST 폴링 + ETag + LocMemCache | `realtime.send` 브로드캐스트 (신호만, 데이터는 재조회) |
| Django 뷰에서 직접 LLM·GitHub 호출 | Edge Functions (Deno), 요청 경로 밖에서 실행 |

**전환 절차와 검증 결과**는 이 저장소의 git 이력에 있다 — 마이그레이션 순서, 리허설 결과,
전환 당일 체크리스트는 커밋 로그와 `supabase/scripts/migrate-from-django.sql`의 주석을 본다.
2026-09-17 기준 데이터 이전 완료, Render는 롤백 창(1주)이 끝나면 삭제한다.

**곁들여 다시 검토한 것 — 로그인 식별자.** 처음엔 "아이디로 로그인하면 아이디→이메일 조회
엔드포인트가 통째로 이메일 열람 구멍이 된다"는 이유로 이메일 전용 로그인을 택했다. 이후
사용자 요청으로 아이디 로그인을 다시 허용했는데, 조회를 클라이언트에 주는 대신 **서버
(Edge Function) 안에서만** 하고, 존재하지 않는 아이디와 틀린 비밀번호가 **같은 오류**를
내도록 만들어 구멍을 막았다(`supabase/functions/login/index.ts`). 원래 우려는 유효했고,
해법은 "안 하기"가 아니라 "클라이언트에 노출하지 않기"였다.

## 2.2 AI 기능: 어디에 쓰고 어디에 안 쓰는가

세부 근거와 판정 과정은 [DEVELOPMENT.md의 "AI 활용 설계"](../DEVELOPMENT.md)에 있다. 여기는
결론만 압축한다.

**쓰는 곳 (둘 다 구현 완료):**
- **참가자 프로필 태그 추출** — 자기소개 한 문단 → 기술 스택·관심사·역할·숙련도. 참가자당 1회,
  실패해도 화면이 막히지 않는다.
- **심사 보조: 제출 저장소 사전 분석** — 운영자가 심사 시작 **전**에 트리거. "무엇이 구현됐고
  무엇이 껍데기인지"만 근거 경로와 함께 제시하고, **점수는 절대 제안하지 않는다**(앵커링 방지 —
  경쟁 제품 DoraHacks의 "스마트 스코어링" 대비 의도적으로 신중한 설계).

**안 쓰는 곳과 이유:**

| 항목 | 이유 |
|---|---|
| 팀 매칭 순위 | 결정적이고 설명 가능해야 한다("왜 나는 저 팀에 못 갔나"). 규칙 기반 점수(역할 45·관심사 25·빈 슬롯 20·스택 10) 유지 |
| 자동 채점 / 점수 제안 | 제안 점수가 뜨면 심사위원이 거기 닻을 내려 결국 모델이 채점하는 것과 같아진다 |
| 표절·중복 탐지 | 오탐의 대가가 비대칭이다(부정행위 혐의). 대신 저장소 첫 커밋 시각이 대회 시작보다 이른지만 보여주고 판단은 심사위원이 한다 |
| 심사위원 간 점수 편차 보정 | 통계(outlier drop)로 풀 문제였지만, 실사용 심사위원이 3~4명이라 표본 부족으로 적용 보류 |

**설계 원칙 하나:** 요청 경로(대회 당일, 시간 압박이 있는 곳)에는 LLM을 절대 넣지 않는다.
허용되는 자리는 참가자당 1회 / 운영자가 시점을 고르는 일괄 실행 / 대회 종료 후 셋뿐이다.

## 2.3 경쟁 제품 대비 차별점

전체 조사(Devpost·HackerEarth·Gavel·CTFd·dribdat 등 비교)는 git 이력의
`docs/research/similar-projects.md`(2026-09-08)에 있다. 남는 결론:

- **LLM 태그 추출 + 규칙 기반 추천 점수의 결합** — 조사 범위에서 이 조합을 하는 곳이 없었다.
  Devpost는 사람이 직접 훑는 필터링, DevMatch는 LLM이 아닌 자체 모델이다.
- **결선 점수를 시상 전까지 숨기고, 시상식에서 등수 순서대로 리빌** — 이 정도로 세분화된
  공개 시점 제어는 조사 대상 중 없었다.
- **발표 교체 시간에는 타이머가 안 돈다** — 늦는 팀이 다음 팀 시간을 깎아먹지 않는다.
- **서버가 API 레벨에서 강제하는 대회 상태 머신** — UI 숨김이 아니라 RLS+트리거로 막는다.
- **참고할 만한 대안(채택 안 함):** Gavel의 페어와이즈(Crowd-BT) 채점 — 캘리브레이션 문제가
  구조적으로 없지만, 결과가 "순위"이지 "점수"가 아니라 실시간 스코어보드·시상 등급 컷과
  충돌해 채택하지 않았다. 팀·심사위원 규모가 커지면 재검토 대상.
